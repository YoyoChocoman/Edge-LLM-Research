# 實驗二：微觀串流延遲動態分析 (Per-Chunk Streaming Latency Dynamics)

## 1. 研究問題

儘管實驗一證明了輸出長度與總解碼時間之間存在總體上的線性關係，但在單次連續生成過程中，其邊際生成成本（每個 chunk 的耗時）是否保持恆定？

本實驗旨在探討微觀層級的延遲動態——具體而言，即區塊間的到達延遲（Inter-chunk arrival latency, $\Delta t_i$）——以確定在生成過程中，解碼速度是保持平穩、平滑退化，還是呈現出離散或非線性的轉變。

## 2. 研究方法
- **指標定義：** 我們量測了應用層觀察到的區塊間延遲（Application-Observed Inter-Chunk Latency, $\Delta t_i = t_i - t_{i-1}$），採用了 Python time.perf_counter() 的高解析度單調時間戳。首字延遲（TTFT）被嚴格從此資料集中隔離，以防初始化開銷（initialization overhead）造成解碼指標的偏誤。
- **硬體與模型：** NVIDIA GeForce RTX 5070 Ti、Meta-Llama-3-8B-Instruct-Q4_K_M.gguf、llama-cpp-python
- **工作負載（Workload）：**　$N = 20$ 次獨立且循序的執行、固定的決定性提示詞（`temperature = 0.0`）、以及會觸及自動停止的最大生成限制（`Max Tokens = 500`）
- **工具：** 我們開發了客製化的 Python 效能側寫腳本，用於時間戳收集、目標異常偵測（`analyze_anomaly.py`）、階梯式墊高現象的統計驗證（`verify_step_up.py`）

## 3. 觀察結果
將區塊間延遲繪製於生成位置對應的圖表上，揭露了高度不均勻的延遲分佈。我們識別出五個值得進一步調查的顯著現象：

*   **a. 初始暖機開銷（Initial Warm-up Overhead）：** 即使隔離了 TTFT，Chunk 1–5 在穩定前仍表現出較高的延遲（約 9.0 ms），這可能源於初始生成器的實體化（instantiation）或 C++/Python 邊界的處理開銷。
*   **b. 輕微的延遲抬升（~Chunk 70）：** 在 Chunk 70 左右，P50 延遲發生了輕微但可見的上升，從約 7.4 ms 增加至約 7.5 ms，且後續並未回降。
*   **c. 巨大的決定性突刺（~Chunk 108）：** 在所有的測試執行（runs）中，於完全相同的生成位置一致性地出現了單一個巨大的延遲突刺（Spike）。
*   **d. 突刺後的階梯式墊高（Post-Spike Step-Up）：**　在突刺之後，P50 的基準延遲並未回到突刺前的水準；它發生了永久性的向上偏移。
*   **e. 尾部延遲的分散度增加（Increased Tail Latency Spread）：** 在突刺之後，P50 與 P95 之間的差距明顯拉大，暗示在觀測到的延遲分佈中出現了更厚重的尾部（heavier tail）。

## 4. 深度分析：Chunk 108 的異常與階梯式墊高

在本階段，我們將量化分析的焦點專注於觀察結果 (c) 與 (d)。

#### 4.1 異常定位
利用我們針對 Chunk 100–120 區間的異常偵測腳本（`analyze_anomaly.py`），我們發現在全部 20 次執行中，該突刺精確發生在 Chunk 108。在此確切時刻生成的內容一致為字串 ' user'（上下文：". In the user's sentence,"）。該特定區塊的延遲飆升至 >10.0 ms，離群值最高達 40.45 ms。


#### 4.2 突刺後墊高現象
為了驗證突刺後的階梯式墊高現象（觀察結果 d），我們在一個乾淨的突刺前視窗（Chunk 53–103）與一個乾淨的突刺後視窗（Chunk 113–163）之間進行了統計比較。

**總體統計分析：**
*   突刺前的全域 P50：**7.3425 ms**
*   突刺後的全域 P50：**7.6867 ms**
*   階梯式墊高差距（Step-up Delta）：**+0.3442 ms （+4.69%）**
*   單次執行的一致性：**20 / 20 次（100.0%）** 皆展現了此延遲墊高現象。

#### 4.3 Token構成合理性檢查
由於串流傳輸的資料區塊（chunk）與產生的 Token 之間並不一定存在一一對應關係，我們進行了一項基於 Token 化的額外合理性檢查。在每次運行中，我們利用相同的 Llama 分詞器（`analyze_token_emission.py`）對累積的串流輸出內容重新進行分詞，併計算出與每個資料區塊相對應的增量 Token 數量。在觀察到的異常點附近，第 108 號資料區塊（Chunk 108）雖然導致累積輸出 Token 數量僅增加了 1 個，卻表現出了顯著延長的延遲；相比之下，第 109 號資料區塊（Chunk 109）在延遲較低的情況下，使累積 Token 數量增加了 2 個。這一現象表明，第 108 號資料區塊出現的延遲激增，無法簡單地歸因於該資料區塊包含的輸出 Token 數量較多。

> *此分析是基於累積的串流文字內容來重構 Token 數量，而非直接監測解碼器內部的 Token 生成過程；因此，所得結果僅作為一項合理性檢查，而非對解碼器逐個 Token 生成迭代過程的精確度量。*

## 5. 討論與假說
在測試配置下，所觀察到的行為具有高度可重複性。針對 Token 構成的合理性檢查進一步表明，第 108 個資料區塊（Chunk 108）出現的延遲激增，無法簡單歸因於該資料區塊內輸出了異常大量的 Token。

因此，現有證據更傾向於支持「依賴狀態的延遲轉變」這一解釋，而非簡單的「單數據塊輸出量效應」。不過，其潛在機制尚無定論。目前我們推測有兩種潛在機制，儘管要確立因果關係仍需進一步進行底層（C++/CUDA）效能側寫分析：
1.  **記憶體配置邊界（Memory Allocation Boundaries）：** 底層引擎（llama.cpp）可能是以預先定義的區塊（blocks）來配置 KV Cache 記憶體。跨越 Chunk 108 可能觸發了區塊的重新配置（reallocation），或者導致活躍的記憶體佔用量超出了特定的快取層級邊界（例如 L2 Cache 上限），進而對後續的讀取造成永久性的延遲懲罰。
2.  **依賴於內容的執行行為（Content-dependent Execution）：** 突刺與特定生成的 Token（' user'）同時發生，因此尚無法完全排除與內容相關的執行效應。然而，若單純由 Token 內容所造成，較難解釋為何在該 Token 出現之後，後續 chunk 的 P50 延遲仍持續維持在較高的水準。

**結論：** 結果顯示，在實驗一中觀測到的總體線性關係，並不意味著區塊間解碼延遲會平滑、線性地增加。在所測試的硬體、模型、執行環境與工作負載下，解碼延遲表現出明顯的非穩定（non-stationary）行為，具體表現為第108個資料區塊處出現可複現的延遲激增、隨後P50延遲持續升高。導致這種狀態轉變的機制尚不明確，有待未來進一步研究。
