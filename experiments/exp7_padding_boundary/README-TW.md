# 實驗 7：有效填充邊界介入

## 1. 研究問題

實驗 6 將週期性的延遲突刺（latency spikes）與有效 KV 範圍擴展、注意力遮罩（attention-mask）形狀改變、拒絕 llama 計算圖重複使用，以及 CUDA Graph 轉換連結了起來。將有效填充（effective padding）的粒度從 **256 更改為 512**，是否會如預期般改變突刺發生的位置？

本實驗對設定邊界的機制進行了介入（intervention）。同時也記錄了延遲成本，但減少總推論時間並非首要的成功標準。

## 2. 研究方法

- **硬體與模型：** NVIDIA GeForce RTX 5070 Ti，`Meta-Llama-3-8B-Instruct-Q4_K_M.gguf`，延續實驗 6 的設定。
- **配置：** 要求完全 GPU 卸載，`n_ctx=2048`，`n_batch=n_ubatch=512`，停用 Flash Attention，貪婪採樣，原生非同步（async）解碼後接續採樣。
- **工作負載：** 一組共用的 123 個 Token 提示詞，以及 **1,024 個解碼步數**的固定重播，涵蓋 `n_past_before_eval=123–1146`。序列匯出（sequence export）刻意持續到超過 EOS（句尾）；這是一個受控的重播，而非一般的回應生成。
- **執行次數：** 每個填充組別（padding group）進行兩批次、每批次 10 次的測量執行，得出**每組 20 × 1,024 = 20,480 個測量步數**。每個進程在測量前會進行 5 步的暖機。
- **執行階段建置：** 兩種加上儀測的變體皆源自同一個本機原始碼快照。建置快取記錄使用了 CUDA Toolkit 12.8 的編譯器、`120a-real`、Release 模式，並啟用 CUDA Graphs。
- **介入：** 僅將 `llama_kv_cache::get_n_kv()` 中的最小有效填充從 `std::max(n_pad, 256u)` 更改為 `std::max(n_pad, 512u)`。比對兩個私有原始碼樹確認了這是它們唯一的檔案內容差異。兩者皆保留了完全相同的追蹤掛鉤（trace hooks）。

執行階段報告所需的填充為 `n_pad=1`；根據變體的不同，有效填充為 256 或 512。對於這種連續、單一序列的重播，在套用 Token 後預期的範圍為：

```text
n_kv = min(KV 容量, ceil((n_past_before_eval + 1) / 填充) × 填充)
```

因此，填充 256 預測在測量範圍內的轉換點為 **256, 512, 768, 1024**，而填充 512 預測的轉換點僅在 **512, 1024**。這改變了有效的注意力範圍，而非已分配的 KV 容量。

事件在測量期間被緩衝儲存，並與每個原生步數對齊。`decode_ms` 測量主機端（host-side）的 `llama_decode()` 區間。`core_decode_ms` 涵蓋了序列移除、批次設定、解碼與採樣，其中包含了在採樣期間等待的未完成 GPU 工作。這兩項指標都不是單純的 GPU 核心（kernel）執行時間。

在每個目標位置 `p`，分析也會測量包含 **p 與 p+1** 的兩步視窗，涵蓋了邊界與隨後的擷取（capture）。其局部參考值使用 `[p−3, p+4]` 內的穩定位置，並排除了所有目標視窗、最初的兩個步數，以及從任一組觀察到的執行階段事件位置。兩步過高量（two-step excess）會在取中位數之前針對每次執行進行計算：

```text
latency[p] + latency[p+1] − 2 × 局部中位數
```

目標步數的突刺必須同時超出其局部參考值達 **20% 且超過 0.8 毫秒**。狀態轉換的檢查獨立於此計時閾值之外。

## 3. 觀察結果

### 3.1 突刺位置跟隨填充介入而改變

| 評估前的 Token 數 | 填充 256 解碼 P50 | 填充 512 解碼 P50 | 解碼突刺發生率，256 / 512 | KV/遮罩 轉換發生率，256 / 512 |
| :--- | :--- | :--- | :--- | :--- |
| **256** | 3.257 ms | **0.453 ms** | **20/20 / 0/20** | **20/20 / 0/20** |
| **512** | 3.395 ms | 3.201 ms | **20/20 / 20/20** | **20/20 / 20/20** |
| **768** | 3.171 ms | **0.404 ms** | **20/20 / 0/20** | **20/20 / 0/20** |
| **1024** | 3.060 ms | 2.973 ms | **20/20 / 20/20** | **20/20 / 20/20** |

核心解碼的突刺分類在這四個位置給出了相同的發生率。填充 512 移除了在 256 與 768 處的事件，同時保留了在 512 與 1024 處的事件。觀察到的復發週期從 256 個 Token 變成兩倍的 512 個 Token；突刺並不是單純在未改變的位置上變小。

![不同有效填充設定下的延遲比較圖](figures/latency_comparison.png)

曲線顯示了每組 20 次執行在各個位置的 P50 值，已排除最初的兩個解碼步數。

### 3.2 執行階段轉換隨突刺移動

| 評估前的 Token 數 | 填充 256 有效 `n_kv` | 填充 512 有效 `n_kv` | llama 計算圖，256 / 512 | CUDA 路徑，256 / 512 |
| :--- | :--- | :--- | :--- | :--- |
| **256** | **256 → 512** | 512 → 512 | 重新建立 / 重複使用 | 直接執行 / 重複使用 |
| **512** | **512 → 768** | **512 → 1024** | 重新建立 / 重新建立 | 直接執行 / 直接執行 |
| **768** | **768 → 1024** | 1024 → 1024 | 重新建立 / 重複使用 | 直接執行 / 重複使用 |
| **1024** | **1024 → 1280** | **1024 → 1536** | 重新建立 / 重新建立 | 直接執行 / 直接執行 |

表列的每一個轉換皆發生在 **20/20 次執行**中。注意力遮罩的形狀為 `[n_kv, 1, 1, 1]`；當範圍改變時，其相容性檢查就會失敗。CUDA 擷取緊接在下一步發生，並於再下一步恢復重複使用。在 256 與 768 處，填充 512 保留了兩種計算圖重複使用的路徑，且不需要隨後的擷取。

除了最初兩步的暫態（transient）之外，完整的追蹤紀錄中未包含這些邊界/擷取對（boundary/capture pairs）以外的額外轉換位置。**兩組的 KV 容量皆維持在 2048**，且每個觀察到的範圍皆符合填充預測。

![每組第 1 次執行觀察到的邊界狀態](figures/boundary_states_run1.png)

此圖顯示了每組第一輪（run 1）的彙整情況，並非成對測量。表格總結了所有 20 次執行的結果；單次執行的延遲幅度可能會與彙整的 P50 有實質上的差異。

### 3.3 被移除的事件不會以「下一步擷取」的形式重新出現

| 評估前的 Token 數 | 兩步解碼過高量，填充 256 | 兩步解碼過高量，填充 512 | 兩步核心過高量，填充 256 | 兩步核心過高量，填充 512 |
| :--- | :--- | :--- | :--- | :--- |
| 256 | +3.776 ms | **+0.098 ms** | +4.873 ms | **+0.197 ms** |
| 512 | +4.691 ms | +4.793 ms | +5.505 ms | +5.658 ms |
| 768 | +3.588 ms | **+0.072 ms** | +4.371 ms | **+0.125 ms** |
| 1024 | +3.555 ms | +3.229 ms | +4.149 ms | +3.791 ms |

這些是在單次執行內計算出的過高量中位數，而非獨立彙整後中位數之間的差異。在 256 與 768 處接近零的過高量，與邊界轉換及其後續擷取雙雙消失的情況相吻合。在保留下來的邊界上，這兩步的成本依然可觀。

### 3.4 較低的解碼呼叫時間並不能確立整體的加速

| 指標 | 填充 256 | 填充 512 | 改變幅度 |
| :--- | :--- | :--- | :--- |
| 單次執行 `decode_ms` 總和，P50 | 487.610 ms | 465.516 ms | **−4.53%** |
| 單次執行 `core_decode_ms` 總和，P50 | 8091.074 ms | 8127.046 ms | **+0.44%** |
| 穩定位置 `core_decode_ms`，彙整 P50 | 7.755 ms | 7.798 ms | **+0.55%** |

單次執行的總和涵蓋了所有 1,024 個測量步數，包含初始的暫態。它們排除了分開計時的預填，且並非完整的應用程式掛鐘（wall-clock）測量；殘留的預填工作可能會影響第一個非同步步數。穩定位置的統計數據對兩組使用了相同的排除位置集合。

累積的解碼呼叫區間減少了，但完整的測量核心區間卻沒有。使用平均值進行加法分解，填充 512 使每次執行的解碼時間減少了 **22.014 毫秒**，但採樣時間卻增加了 **67.714 毫秒**；平均總核心時間增加了 **45.676 毫秒**（包含其餘的小組件）。由於採樣包含了 GPU 等待時間，因此這並不是採樣演算法本身變慢的證據。

早期的穩定區域說明了這種權衡：在評估前位置 **125–255**，填充 512 已經在使用 512 的範圍而非 256。彙整的核心 P50 為 **8.014 毫秒對比 7.512 毫秒**。雖然這些計時資料本身無法隔離出差異的來源，但較大的範圍除了會改變計算圖的行為，也可能改變一般步數的工作量。在剩餘的上下文區域中，延遲並沒有呈現出一致較低或較高的趨勢。

批次層級（Batch-level）的核心總量 P50，在填充 256 時為 **8093.369 / 8084.749 毫秒**，在填充 512 時為 **8102.946 / 8151.311 毫秒**。保存的紀錄並未確立隨機或平衡的執行順序，也沒有保存時脈或溫度的遙測數據。因此，整體的小幅差異應被視為描述性觀察，而非對一般效能退化或提升的宣稱。

### 3.5 重播完整性與採樣 Token 的差異

重新對齊所有四份原始追蹤紀錄，可重現保存的分析步驟與目標統計數據。所有 40 次測量執行皆共用相同的提示詞 Token、評估 Token 序列、預期 Token 序列、上下文設定與暖機次數，並與 `results/sequence.txt` 相符。

每個填充 256 的批次包含 **51,240 個事件**；每個填充 512 的批次包含 **51,220 個事件**。所有批次皆為 **零事件遺失（zero dropped events）**。沒有發現填充範圍不符，或組內採樣 Token 出現變異的情況。

然而，這兩組在四個採樣 Token 位置上有所不同：

| 解碼步數 | 評估前的 Token 數 | 填充 256 / 匯出器 Token | 填充 512 Token |
| :--- | :--- | :--- | :--- |
| 461 | 583 | 1359 | 498 |
| 578 | 700 | 264 | 323 |
| 596 | 718 | 701 | 279 |
| 869 | 991 | 358 | 374 |

每一處差異皆出現在所有 20 次填充 512 的執行中，與匯出器參考值（exporter reference）相比，產生了 **80 筆不匹配的步數紀錄**。填充 256 則自始至終與參考值相符。這兩種變體仍然在評估相同的固定輸入 Token，因此這些採樣上的差異不會改變重播的工作負載。但這確實使得我們無法宣稱它們具備完全一致的貪婪輸出；邏輯值（logits）與任務品質並未被評估。

## 4. 結論

**將有效填充從 256 更改為 512，會如預期般改變觀察到的邊界突刺與相關執行階段轉換的復發情況。** 在 256 與 768 處計時突刺與狀態轉換雙雙消失，提供了基於介入操作的證據，證明在受測配置中，有效填充邊界控制了這種週期性機制。

結合實驗 6 的結果，這些證據支持了從有效 KV 範圍擴展，到遮罩形狀不相容、llama 計算圖重新建立、CUDA 直接執行，以及下一步擷取的這條連鎖反應。它並未將各組件的延遲貢獻隔離出來、也未證明後端 KV 記憶體分配有所增長，或是確立單獨由遮罩建構所造成的成本。

此介入操作將重播中的週期性邊界轉換次數減半，但**並未展現出整體的加速**。這兩種變體皆有加上儀測，且它們的事件頻率不同；需要進行未插樁的效能比較，才能評估部署上所帶來的實質效益。結果仍然侷限於特定的一種模型、裝置、重播，以及停用 Flash Attention 的配置。實驗 7 的主要問題已獲得解答；至於效能最佳化與數值等效性的評估，則依然是獨立待解的問題。
