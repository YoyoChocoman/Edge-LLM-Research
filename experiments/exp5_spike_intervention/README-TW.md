# 實驗五：系統參數消融與長上下文動態分析

## 1. 研究問題
在先前的實驗中，我們發現了與總上下文長度（Total Context Length）邊界（約 256 tokens）嚴格綁定的決定性延遲突刺（deterministic latency spike）與階梯式墊高（step-up）現象。本實驗旨在縮小潛在原因的範圍，並回答以下問題：
1. 執行期設定（`n_ctx` 或 `n_batch`）是否決定了這些突刺的發生位置？
2. 這種突刺的週期性是否在更長的序列（>1000 tokens）中依然存在？
3. 在開啟 Flash Attention (FA) 的情況下，基礎解碼延遲（TPOT）在長序列中是否保持絕對恆定，還是依然會隨上下文長度增加而變大？

## 2. 實驗方法
- **介入策略**：單一變因法（One-Factor-At-A-Time, OFAT）參數消融。
- **固定變數**：硬體（RTX 5070 Ti）、模型（`Meta-Llama-3-8B-Instruct-Q4_K_M`）、Flash Attention = `ON`、`temperature = 0.0`
- **測試次數**：所有階段中，每個變數設定與每個 Prompt 皆重複執行 20 次（Runs = 20）。
- **第一階段（`n_ctx` 消融）**：將 `n_ctx` 變數設定為 `[256, 512, 1024, 2048]` 進行掃描。使用先前實驗中的 Prompt A、B 與 C。
- **第二階段（`n_batch` 消融）**：將 `n_batch` 變數設定為 `[128, 256, 512, 1024]` 進行掃描。使用先前實驗中的 Prompt A、B 與 C。
- **第三階段（長上下文測試）**：將 `max_tokens` 延伸至 ~2000，以觀察長期的串流動態與週期性。使用全新的 Prompt（`LONG_PROMPT`）。

## 3. 觀察結果

### 3.1 突刺位置不受 `n_ctx` 影響
我們假設所配置的最大上下文大小（`n_ctx`）可能決定了記憶體區塊的邊界。然而，跨越多個 Prompt 的測試顯示，將 `n_ctx` 從 512 改變至 2048 並未使突刺位置發生偏移。
> 當 `n_ctx=256` 時未觀察到突刺，因為生成在觸及邊界前便已截斷。對於所有其他設定值，突刺位置皆嚴格固定在 Total Context = 241 與 497。

> 下列數據僅顯示 Prompt A 的結果

| 實驗設定 | Input Toks | Spike Chunk | Total Ctx | Spike P50 |
| :--- | :--- | :--- | :--- | :--- |
| **n_ctx: 512** | 133 | 108 | **241** | 12.28 ms |
| **n_ctx: 1024** | 133 | 108 | **241** | 13.13 ms |
| **n_ctx: 2048** | 133 | 108 | **241** | 12.94 ms |

**結論**：在所測試的 `n_ctx` 設定中，觀察到的突刺位置保持不變。

### 3.2 突刺位置不受 `n_batch` 影響
我們假設 Prompt 處理/生成的批次大小（`n_batch`）可能觸發了同步邊界（synchronization boundaries）。然而，跨越多個 Prompt 的測試顯示，將 `n_batch` 從 128 改變至 1024 並未使突刺位置發生偏移。
> 下列數據僅顯示 Prompt B 的第一個突刺結果

| 實驗設定 | Input Toks | Spike Chunk | Total Ctx | Spike P50 |
| :--- | :--- | :--- | :--- | :--- |
| **n_batch: 128** | 161 | 80 | **241** | 10.68 ms |
| **n_batch: 256** | 161 | 80 | **241** | 10.36 ms |
| **n_batch: 512** | 161 | 80 | **241** | 10.27 ms |
| **n_batch: 1024** | 161 | 80 | **241** | 9.67 ms |

**結論**：在所測試的 `n_batch` 設定中，觀察到的突刺位置保持不變。

### 3.3 長上下文中嚴格的 256-Token 週期性
藉由將生成長度延伸至約 1800 個 chunks，我們觀察到了完美重複的延遲突刺模式。

| Spike Index | Total Context | Distance from Prev. Spike | Spike P50 |
| :--- | :--- | :--- | :--- |
| Spike 1 | 497 | - | 11.14 ms |
| Spike 2 | 753 | **256** | 10.60 ms |
| Spike 3 | 1009 | **256** | 10.07 ms |
| Spike 4 | 1265 | **256** | 10.33 ms |
| Spike 5 | 1521 | **256** | 10.97 ms |
| Spike 6 | 1777 | **256** | 10.73 ms |
| Spike 7 | 2033 | **256** | 11.53 ms |

> **備註**：長上下文負載使用了 368 個 tokens 的 Input。因此，先前在 Total Context = 241 觀察到的初始突刺，落於本次實驗的可觀測範圍之外。

**結論**：延伸實驗證明了在 Total Context = 241 的初始事件後，觀測到的延遲突刺會以精確的 256 tokens 週期重現。這種現象在測試的 `n_ctx` 與 `n_batch` 設定中皆保持不變，暗示此週期性是由未直接暴露於這些參數的底層機制所控制。固定粒度的記憶體管理或 KV-Cache 機制是合理的解釋，但本實驗並未直接觀測到記憶體配置、分頁（paging）、快取管理事件或相對應的 CUDA 操作。

### 3.4 長期的 TPOT 退化（即使開啟 Flash Attention）
在實驗四中，Flash Attention 大幅減輕了第一次突刺後觀察到的持續性階梯式墊高（step-up）。然而，長上下文延伸實驗揭露了另一種現象：隨著上下文增長，基礎解碼延遲呈現逐漸上升的趨勢。

| Spike Context Boundary | Before P50 (ms) | After P50 (ms) | Step Delta (ms) |
| :--- | :--- | :--- | :--- |
| 497 | 7.7442 | 7.7244 | -0.0199 ms |
| 753 | 7.5162 | 7.6275 | +0.1113 ms |
| 1009 | 7.7997 | 7.7965 | -0.0032 ms |
| 1265 | 8.0940 | 8.1819 | +0.0879 ms |
| 1521 | 8.3213 | 8.4739 | +0.1526 ms |
| 1777 | 8.6067 | 8.6381 | +0.0313 ms |
| 2033 | 8.8103 | 8.9290 | +0.1187 ms |

> 從大約 Context 500 到 Context 2000，中位數的單字元輸出時間（TPOT）呈現了從約 **7.5 ms** 緩步上升至 **8.9 ms** 的向上趨勢。長上下文軌跡亦顯示，在接近 500 tokens 的第一個可觀測邊界附近出現了短暫的平穩期（plateau），隨後長期上升的趨勢才繼續。

**分析**：邊界之間的階梯變化差值（step deltas）很小且正負號不一致。這表明主導長上下文效應的，並非每一個 256-token 邊界上固定的持續性階梯式墊高，而是基礎解碼延遲隨著上下文長度增加而產生的漸進式上升。

**結論**：雖然 Flash Attention 大幅壓制了早期實驗中觀察到的持續性階梯式墊高，但它並未消除依賴上下文長度而增加的解碼延遲。所觀察到的漸進式退化，與日益增長的 KV-Cache 所帶來的計算與記憶體存取成本增加的物理現象一致。

## 4. 次要觀察與未解現象
在長上下文實驗中觀察到了幾個次要行為。為求完整性將其記錄於此，但不作為主要因果關係的發現。

### 4.1 初始解碼瞬態現象 (Initial Decoding Transient)
前幾個解碼 chunk 在進入長期趨勢前，表現出獨特的延遲行為。這可能反映了初始化效應、從 Prompt 到生成的轉換行為，或其他的框架/執行期狀態改變。本實驗並未孤立出其根本原因。

### 4.2 邊界局部的變異性 (Boundary-Local Variability)
部分 256-token 邊界產生了微小的延遲下降（step-down）或趨近於零的 P50 延遲變化。例如：
- Context 497: -0.0199 ms
- Context 1009: -0.0032 ms

其他邊界則產生微小的正向變化。相較於長期的上升趨勢，這些變化十分微小，不足以確立為一個獨立的機制。因此，它們被視為邊界局部的變異性，而非獨立建立的現象。

### 4.3 P95 尾部延遲擴張 (P95 Tail-Latency Expansion)
長上下文軌跡亦顯示，在某些區域中 P50 與 P95 延遲之間的差距逐漸拉大。這表示在長上下文解碼的部分過程中，尾部延遲（tail latency）變得更大。然而，本實驗並無法確認此行為是由 GPU 排程、記憶體競爭、執行期同步或其他機制所引起。需進一步的 profiling 才能確定尾部延遲擴張的來源。

## 5. 結論
實驗五確立了三個主要觀察結果。

### 發現 1：高階執行期參數無法使突刺偏移
在測試的設定中，只要相關的上下文位置是可觸及的，觀察到的突刺位置皆保持不變。特別是第一個可觀測突刺始終維持在 Total Context = 241。這表明突刺的位置並非由所測試的 `n_ctx` 或 `n_batch` 設定直接決定。

### 發現 2：突刺每 256 Tokens 週期性重現
長上下文實驗獨立觀測到了以下突刺位置（包含早期觀測）：

```text
241 -> 497 -> 753 -> 1009 -> 1265 -> 1521 -> 1777 -> 2033

Δ = 256 tokens
```

實驗提供了強而有力的證據，證明這是一個可重現的 256-token 週期性現象。然而，導致此週期性的底層執行期事件仍未被確認。

### 發現 3：Flash Attention 無法消除長上下文的 TPOT 增長
Flash Attention 大幅減少了早期實驗中觀察到的持續性階梯式墊高。然而，即使啟用了 Flash Attention，基礎解碼延遲仍會隨著上下文增長而上升。
觀察到的趨勢大約為：

```text
~7.5 ms at Context ~500
        ↓
~8.9 ms at Context ~2000
```

此行為與日益增長的 KV-Cache 所導致的注意力計算及記憶體存取成本增加相符。

---

實驗五縮小了決定性延遲突刺潛在原因的範圍。突刺位置在測試的 `n_ctx` 與 `n_batch` 設定下保持不變，同時長上下文生成展示了超過 2000 個總上下文 tokens 的可重現 256-token 週期性。與此同時，Flash Attention 並無法完全消除依賴上下文長度而增加的基礎解碼延遲。因此，實驗五的主要結論為：

> **延遲突刺是一個可重現的 256-token 週期性現象，且不受所測試的高階執行期參數直接控制；同時，長上下文解碼展現了另一種基礎 TPOT 逐漸上升的獨立現象。**

底層的執行期機制依然未解。要確認該機制，需要低階的檢測埋點（low-level instrumentation），而非進一步的高階參數消融。
