# 實驗 6：執行階段層級驗證與突刺定位

## 1. 研究問題

實驗 2 至 5 在應用程式觀察到的串流中，識別出可重現且與上下文相關的延遲突刺（latency spikes）。這些週期性的突刺發生在本地推論堆疊（inference stack）的哪一層？又有哪些內部執行階段（runtime）的轉換伴隨其發生？

實驗 6 沿著證據的軌跡，從直接的 Python 綁定呼叫、原生的 C++ 解碼，最終追蹤至內部執行階段的狀態。其目標是在受測配置中定位此現象，並找出其觸發機制。

## 2. 研究方法

- **硬體與模型：** NVIDIA GeForce RTX 5070 Ti，`Meta-Llama-3-8B-Instruct-Q4_K_M.gguf`。
- **共用設定：** GPU 卸載，`n_ctx=2048`，停用 Flash Attention，以及貪婪採樣。原生執行使用 `n_batch=n_ubatch=512`，其餘上下文設定使用原生預設值。
- **工作負載：** 固定 123 個 Token 的提示詞，5 步的暖機，每種配置進行 20 次 500 個解碼步數的測量執行。實驗 B 與 C 重播（replay）了從實驗 A 首次執行中所匯出的已評估 Token ID。
- **位置對齊：** 解碼步數 134 與 390 對應於 `n_past_before_eval = 256` 與 `512`。此計數描述的是評估下一個 Token 前的位置；它與執行階段經過填充後的 `n_kv` 不同。

| 階段 | 測量邊界 | 目的 |
| :--- | :--- | :--- |
| [實驗 6-A：直接 Python 綁定](a_python_binding_decode/README.md) | `llm.eval()` 與 `llm.sample()` | 測試在移除高階格式化與串流迭代後，突刺是否依然存在 |
| [實驗 6-B：原生解碼](b_native_llama_decode/README.md) | 獨立的 C++ `llama_decode()`、同步操作與採樣 | 測試是否必須依賴 Python，並將 GPU 等待時間從採樣中分離 |
| [實驗 6-C：執行階段狀態追蹤](c_runtime_state_trace/README.md) | KV 範圍、遮罩相容性、llama 計算圖重複使用與 CUDA Graph 狀態 | 識別與突刺對齊的執行階段轉換 |

實驗 B 連結了已安裝綁定的共享函式庫。實驗 C 則使用同一個本地原始碼快照，分別建置了未插樁（uninstrumented）的基準測試版與已插樁的追蹤版，並使用 CUDA Toolkit 12.8 為 `120a-real` 編譯，同時啟用 CUDA Graphs。

實驗 B 與 C 皆比較了**非同步（async）**解碼後接採樣的模式，與在採樣前插入 `llama_synchronize()` 的**同步（sync）**模式。實驗 C 更進一步在每種模式中比較了未插樁的基準測試與追蹤版本。

突刺的分類要求延遲必須超出單次執行在 ±3 個位置內的局部中位數達 **20% 且超過 0.8 毫秒**。排除相鄰位置與參考值彙整的方式已在各子實驗中詳細記錄。實驗 A 報告的組件過高量（component excess）使用了彙整後的局部參考值；實驗 B 與 C 則報告成對超出量中位數（median paired excess）。這些過高的統計數據不應被視為可直接互換比較的。

## 3. 觀察結果

### 3.1 突刺跨越不同測量層級依然存在

| 階段 / 配置 | 測量區間 | 256 時的 P50 | 512 時的 P50 | 各邊界的突刺發生率 |
| :--- | :--- | :--- | :--- | :--- |
| A: Python 綁定 | 評估 (Eval) | 2.890 ms | 2.872 ms | **20/20** |
| B: 原生 非同步 | 解碼 (Decode) | 2.649 ms | 2.835 ms | **20/20** |
| B: 原生 同步 | 解碼 (Decode) | 2.713 ms | 3.364 ms | **20/20** |
| C: 基準測試 非同步 | 解碼 (Decode) | 2.864 ms | 3.468 ms | **20/20** |
| C: 追蹤版 非同步 | 解碼 (Decode) | 3.102 ms | 2.926 ms | **20/20** |
| C: 基準測試 同步 | 解碼 (Decode) | 2.952 ms | 3.350 ms | **20/20** |
| C: 追蹤版 同步 | 解碼 (Decode) | 2.693 ms | 3.048 ms | **20/20** |

實驗 A 在繞過聊天格式化與串流迭代後保留了週期性突刺。實驗 B 證明在其測量迴圈中無需 Python 即可重現突刺。實驗 C 的未插樁建置版本在啟用內部追蹤之前，也重現了突刺。

**觀察結論：** 高階串流、Python 執行與插樁皆非邊界突刺發生的必要條件。這些證據將該可重現的事件定位於原生執行階段或更底層。

該表格比較的是重現率與發生位置，而非等效的執行成本。因為 Python 與原生設定、預填的處理方式以及執行階段的建置版本皆不同；絕對的 P50 數值無法用來對各個階段進行效能排序。

### 3.2 採樣時間包含等待未完成的 GPU 工作

實驗 A 的局部評估（eval）區間大約為 **0.4–0.5 毫秒**，而在週期性邊界附近的採樣大約佔用了 **6.7–6.9 毫秒**。兩者結合的延遲保持在 **7–8 毫秒**左右。

實驗 B 的同步比較解釋了為何短暫的評估區間不代表完整的 Token 步數也同樣短暫：

| 評估前的 Token 數 | 非同步 採樣 P50 | 同步模式 同步 P50 | 同步模式 採樣 P50 |
| :--- | :--- | :--- | :--- |
| 256 | 7.293 ms | 7.119 ms | **0.100 ms** |
| 512 | 7.184 ms | 6.882 ms | **0.099 ms** |

明確的同步操作將大部分的等待時間移入其專屬的同步區間，而週期性的解碼突刺依然存在。因此，非同步的採樣時間絕不能單純解釋為僅是貪婪採樣的運算成本。

### 3.3 形狀轉換導致拒絕重複使用計算圖

實驗 C 在**兩種追蹤模式的所有 20 次執行中**紀錄了下列序列：

| 評估前的 Token 數 | 有效 `n_kv` | 套用 Token 後的遮罩形狀 | llama 計算圖 | CUDA Graph 路徑 |
| :--- | :--- | :--- | :--- | :--- |
| **256** | **256 → 512** | **`[512, 1, 1, 1]`** | **重新建立** | **直接執行** |
| 257 | 512 | `[512, 1, 1, 1]` | 重複使用 | 擷取 (Capture) |
| 258 | 512 | `[512, 1, 1, 1]` | 重複使用 | 重複使用 |
| **512** | **512 → 768** | **`[768, 1, 1, 1]`** | **重新建立** | **直接執行** |
| 513 | 768 | `[768, 1, 1, 1]` | 重複使用 | 擷取 (Capture) |
| 514 | 768 | `[768, 1, 1, 1]` | 重複使用 | 重複使用 |

在評估前位置 256 時，評估下一個 Token 需要 257 個佔用位置。執行階段將填充後的注意力範圍擴展為 512，導致現有的遮罩不再吻合。受檢視的原始碼明確檢查了此維度以決定是否重複使用計算圖；追蹤紀錄顯示該檢查失敗並隨後重新建立計算圖。同樣的轉換發生在 512，將有效範圍擴展至 768。

**在整個追蹤過程中，KV 容量維持在 2048。** 觀察到的擴張涉及的是有效注意力範圍與遮罩形狀，這並非底層 KV 記憶體分配擴充的證據。

在每個邊界，改變的 CUDA Graph 屬性會重置暖機並導致直接執行。擷取（Capture）發生在下一個步數，而非主要邊界事件發生的當下。那些擷取步數也顯示出額外的解碼延遲：在兩種模式下，位置 **257 的追蹤版 P50 為 1.267–1.277 毫秒**，而位置 **513 的追蹤版 P50 為 2.337–2.438 毫秒**。在每個位置上，擷取皆觀察到 20/20 次，即使延遲未達到突刺閾值亦然。

![非同步模式下的執行階段狀態對齊，第 1 次執行](c_runtime_state_trace/figures/trace_async.png)

此圖展示了單次執行的情況；狀態轉換的計數與延遲摘要則涵蓋了每種模式的所有 20 次執行。除了首次解碼與這兩個週期性邊界之外，實驗 C 中並未觀察到 llama 計算圖重新建立的情況。

### 3.4 證據品質與限制

實驗 B 依據實驗 A 匯出的預期結果，驗證了**每種模式下的 10,000 個採樣 Token**。實驗 C 在其四種配置中包含 **40,000 個測量步數**，皆具有一致的重播輸入與位置推進。每份追蹤紀錄包含 **40,040 個事件，且零事件遺失**。

實驗 C 的四種配置產生了完全相同的採樣 Token 軌跡，但在每次執行的解碼第 63 步（`n_past_before_eval=185`），皆與實驗 A 的結果有所不同。由於重播輸入保持固定，這不會改變後續的工作負載；但這確實限制了我們宣稱不同執行階段建置版本間在數值上完全等效的說法。

首次解碼與週期性的復發被分開處理。與實驗 A 不同，實驗 B 與 C 在預填之後不會立即採樣或明確進行同步，因此其首次測量到的解碼可能包含等待未完成的預填工作。

這些結果涵蓋了單一模型、裝置、工作負載與配置。原始碼檢視與追蹤紀錄識別了因形狀改變而拒絕重複使用計算圖的情況，但 API 計時無法將計算圖建立、排程器準備、直接 GPU 執行與擷取等成本分離開來。獨立的基準測試與追蹤版執行也無法精確隔離插樁的額外負擔。本實驗並未確立單靠遮罩擴張就能完全解釋過高的延遲總量。

## 4. 結論

實驗 6 作為一項**執行階段層級與機制定位的研究**已告完成。實驗 A 排除了高階串流作為必要解釋的可能性；實驗 B 顯示不需要 Python 參與；實驗 C 識別出一個可重現的轉換：從填充後的 KV 範圍擴張與遮罩不相容，導致 llama 計算圖重新建立以及 CUDA 直接執行，並伴隨在下一步發生擷取。

因此，週期性突刺被定位於受測堆疊中特定與形狀相關的執行階段轉換。這項結論比單純的位置關聯性更強烈，因為所觀察到的事件與原始碼層級的重複使用條件相符。
