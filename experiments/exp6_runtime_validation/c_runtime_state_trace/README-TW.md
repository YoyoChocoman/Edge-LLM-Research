# 實驗 6-C：內部執行階段狀態追蹤

## 1. 研究問題

實驗 6-B 將週期性的突刺（spikes）定位在原生的 `llama_decode()` 或更底層。當 `n_past_before_eval = 256` 與 `512` 時，執行階段的有效 KV 長度、注意力遮罩（attention-mask）形狀以及計算圖重複使用（graph-reuse）狀態是否會同時改變？

本實驗將內部執行階段事件與固定的 Token 重播進行對齊，藉此區分 llama 計算圖的重複使用與 CUDA Graph 的執行。

## 2. 研究方法

- **硬體與模型：** NVIDIA GeForce RTX 5070 Ti，`Meta-Llama-3-8B-Instruct-Q4_K_M.gguf`。
- **配置：** 要求完全 GPU 卸載，`n_ctx=2048`，`n_batch=n_ubatch=512`，停用 Flash Attention，貪婪採樣；其餘上下文設定使用原生預設值。
- **工作負載：** 與實驗 B 相同的 123 個 Token 提示詞及 500 個 Token 重播，包含 5 步暖機，每種配置連續進行 20 次測量執行。
- **執行階段建置：** 從同一個本地原始碼快照分別建置未插樁（uninstrumented）的基準測試版與已插樁的追蹤版（trace），使用 CUDA Toolkit 12.8，`120a-real`，發布模式（Release mode），並啟用 CUDA Graphs。這些是重新編譯的函式庫，而非實驗 B 所安裝的綁定函式庫。
- **計時模式：** 非同步解碼後接採樣，以及在採樣前插入 `llama_synchronize()` 的同步模式。每種模式皆有其獨立的基準測試與追蹤測量。
- **插樁（Instrumentation）：** 紀錄套用 Token 後的有效填充 `n_kv` 與快取容量、遮罩建立與相容性檢查、llama 計算圖重複使用決策，以及 CUDA Graph 狀態。事件會先緩衝於記憶體中，並在測量結束後寫出。

這四種配置皆包含 **20 × 500 = 10,000 個測量步數**。計時方式保留了實驗 B 對序列移除、批次設定、解碼、同步與採樣的劃分。`core_decode_ms` 涵蓋從序列移除到採樣的整個過程；它不單單僅是 GPU 核心（kernel）的執行時間。

突刺的分類是使用每次執行在目標前後 ±3 個位置內的局部中位數，並排除目標本身、首次解碼以及其他 256-Token 邊界。判定為突刺的條件必須同時超出參考值 **20% 且超過 0.8 毫秒**。成對超出量中位數（Median paired excess）是在每次執行內部計算後才彙整，而不是把獨立彙整後的中位數直接相減。相鄰的擷取（capture）步數仍然符合作為邊界局部參考值的資格。

## 3. 觀察結果

### 3.1 邊界突刺在兩個重新編譯的版本中依然存在

| 模式 | 評估前的 Token 數 | 基準測試 解碼 P50 | 追蹤版 解碼 P50 | 追蹤版 成對超出量中位數 | 解碼突刺發生率，基準測試 / 追蹤版 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Async | **256** | 2.864 ms | 3.102 ms | **+2.620 ms** | **20/20 / 20/20** |
| Async | **512** | 3.468 ms | 2.926 ms | **+2.448 ms** | **20/20 / 20/20** |
| Sync | **256** | 2.952 ms | 2.693 ms | **+2.337 ms** | **20/20 / 20/20** |
| Sync | **512** | 3.350 ms | 3.048 ms | **+2.656 ms** | **20/20 / 20/20** |

未插樁的基準測試版已經能重現這兩個突刺。因此，追蹤插樁並沒有引入突刺或改變其位置。獨立的基準測試與追蹤版執行之間的差異，無法提供對插樁額外負擔（overhead）的乾淨估計值，且追蹤版數值較小也不意味著有速度提升。

在有追蹤的執行中，邊界 `core-decode` 的 P50 為 **11.08–11.18 毫秒**，相比之下局部參考值為 **8.14–8.33 毫秒**。該事件在完整的測量步數以及原生解碼區間內皆清晰可見，儘管 `core-decode` 的突刺發生率並非一致都是 20/20。

### 3.2 KV 範圍與遮罩改變導致拒絕重複使用計算圖

下列序列出現在**兩種追蹤模式的所有 20 次執行中**：

| 評估前的 Token 數 | 有效 `n_kv` | 遮罩形狀 `ne[0..3]` | llama 計算圖 | CUDA Graph 路徑 |
| :--- | :--- | :--- | :--- | :--- |
| 255 | 256 | `[256, 1, 1, 1]` | 重複使用 | 重複使用 |
| **256** | **512** | **`[512, 1, 1, 1]`** | **重新建立** | **直接執行** |
| 257 | 512 | `[512, 1, 1, 1]` | 重複使用 | 擷取 (Capture) |
| 258 | 512 | `[512, 1, 1, 1]` | 重複使用 | 重複使用 |
| 511 | 512 | `[512, 1, 1, 1]` | 重複使用 | 重複使用 |
| **512** | **768** | **`[768, 1, 1, 1]`** | **重新建立** | **直接執行** |
| 513 | 768 | `[768, 1, 1, 1]` | 重複使用 | 擷取 (Capture) |
| 514 | 768 | `[768, 1, 1, 1]` | 重複使用 | 重複使用 |

在每個邊界上，遮罩相容性檢查在**每種模式的 20/20 次執行中皆失敗**，並重新建立 llama 計算圖。除了首次解碼與這兩個邊界之外，並未觀察到其他 llama 計算圖被重新建立。

受檢視的原始碼對有效的 KV 範圍進行填充（padding），以保持邊界間計算圖形狀的穩定。在評估前位置 256 時，評估下一個 Token 需要 257 個佔用位置，因此填充後的範圍擴展為 512。下一次的轉換同樣將 512 擴展為 768。遮罩相容性明確要求其第一個維度必須等於 `n_kv`，這將形狀改變與拒絕重複使用計算圖產生了關聯。

**在整個追蹤過程中，KV 容量維持在 2048。** 觀察到的變化是有效注意力範圍與遮罩形狀，這並非底層 KV 記憶體分配擴充的證據。其他的計算圖或排程器（scheduler）分配則沒有獨立進行測量。

### 3.3 CUDA 擷取發生在邊界的下一步

在 256 與 512 時，CUDA 追蹤報告了改變的計算圖屬性，重置了計算圖暖機，並採直接執行。在 257 與 513 時，屬性保持穩定，暖機完成，並發生擷取（capture）。正常的 CUDA Graph 重複使用於 258 與 514 恢復。

| 模式 | 擷取位置 | 追蹤版 解碼 P50 | 成對超出量中位數 | 解碼突刺發生率 |
| :--- | :--- | :--- | :--- | :--- |
| Async | 257 | 1.277 ms | +0.834 ms | 14/20 |
| Async | 513 | 2.337 ms | +1.961 ms | 20/20 |
| Sync | 257 | 1.267 ms | +0.893 ms | 16/20 |
| Sync | 513 | 2.438 ms | +2.040 ms | 20/20 |

擷取在**每種模式的兩個位置上皆觀察到 20/20 次**，即使延遲未達到突刺閾值。這個過渡狀態橫跨了多個步數：主邊界的突刺不能被描述為同一層級的 CUDA 擷取事件。這些計時涵蓋了整個解碼呼叫，而非單獨擷取所耗費的時間。

### 3.4 追蹤完整性與範圍

每份追蹤資料包含 **40,040 個事件，且零事件遺失**。重新對齊原始事件能完美重現所儲存的分析結果。跨四種配置的所有 40,000 個測量步數皆具有預期的位置推進與重播軌跡。

這四種配置也產生了完全相同的採樣 Token 軌跡。在每次執行的解碼第 63 步（`n_past_before_eval=185`），皆與實驗 A 的預期採樣有所不同：預期 Token 為 `2317`，採樣 Token 為 `17571`。由於固定的重播繼續餵入已紀錄的輸入 Token，因此這並不會改變後續的工作負載。但這確實限制了我們無法宣稱此數值與原始 A/B 執行階段完全等效。

在位置 123 的首次解碼與隨後在 124 的擷取，與週期性的復發被分開處理。與實驗 B 一樣，在預填之後沒有立即的明確同步或採樣。此結果涵蓋單一模型、裝置、工作負載與執行階段配置；追蹤並未分解計算圖建立、排程器工作或 GPU 執行的詳細成本。

## 4. 結論

實驗 6-C 識別出與週期性突刺相關的可重現執行階段轉換：**填充後的 KV 範圍擴張改變了注意力遮罩的形狀，拒絕了 llama 計算圖的重複使用，同時伴隨著 CUDA Graph 退回至直接執行，接著在下一個步數進行擷取。**

結合實驗 A 與 B，這足以支持將實驗 6 作為一項執行階段層級與機制定位的研究作結。這項證據比單純的 Token 位置關聯性更強烈，因為所記錄的轉換與原始碼層級的重複使用條件相符。然而，這並未確立單靠遮罩擴張就能完全解釋過高的延遲，也未能將每個下游組件的貢獻進行量化。如果未來的目標轉為因果隔離（causal isolation）或降低延遲，那麼進行受控介入（controlled intervention）將是下一步方向。
