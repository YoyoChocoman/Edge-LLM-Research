# 實驗 6-B：原生 llama.cpp 解碼驗證

## 1. 研究問題

實驗 6-A 顯示，週期性的突刺在直接 Python 綁定評估中依然存在。當從測量的解碼迴圈中移除 Python 時，這些突刺是否仍然存在？且明確的同步操作（explicit synchronization）如何改變歸因於採樣（sampling）的時間？

本實驗使用固定的 Token 重播（token replay），將測量的邊界移至原生的 `llama_decode()` 呼叫。

## 2. 研究方法

- **硬體與模型：** NVIDIA GeForce RTX 5070 Ti，`Meta-Llama-3-8B-Instruct-Q4_K_M.gguf`。
- **配置：** 要求完全 GPU 卸載，`n_ctx=2048`，`n_batch=n_ubatch=512`，停用 Flash Attention；其餘上下文設定使用原生預設值。
- **工作負載：** 123 個 Token 的提示詞（prompt）後接續 500 個評估 Token，包含 5 步的暖機（warm-up），每種模式連續執行 20 次。
- **Token 重播：** `sequence_export.py` 將明確指定的提示詞進行分詞（tokenize），並從實驗 6-A 的首次執行中，將經過評估/預期的下一個 Token ID 複製到 `results/sequence.txt` 中。生成的文字不會重新進行分詞。
- **原生執行：** `run_native.py` 使用已安裝綁定的供應商標頭檔（vendor headers）與共享函式庫來編譯 `native.cpp`。C++ 程式會執行預填（prefill）、Token 重播與貪婪採樣，接著將單步的測量結果直接寫入 JSON 檔案中。

每一個測量步數都區分了序列移除（sequence removal）、批次設定（batch setup）、`llama_decode()`、選擇性的同步操作與採樣。計時使用 `std::chrono::steady_clock`。會將採樣到的 Token 與重播序列進行比對核對。

以下兩種模式被獨立評估：
1. **非同步（Async）：** 解碼後接著採樣，兩者之間沒有明確的同步呼叫。
2. **同步（Sync）：** 在解碼之後與採樣之前，插入 `llama_synchronize()`。

突刺的分類是針對每次執行，取目標位置前後 ±3 個相鄰位置（排除目標本身與其他週期性邊界）的局部中位數作為參考值。判定為突刺的條件是必須同時超出參考值達 **20% 且超過 0.8 毫秒**。

## 3. 觀察結果

### 3.1 週期性突刺在原生解碼呼叫內部依然存在

| 模式 | 評估前的 Token 數 | 解碼 P50 | 局部參考 P50 | 成對超出量中位數 | 突刺發生率 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Async | **256** | 2.649 ms | 0.422 ms | **+2.151 ms** | **20/20** |
| Async | **512** | 2.835 ms | 0.401 ms | **+2.387 ms** | **20/20** |
| Sync | **256** | 2.713 ms | 0.435 ms | **+2.253 ms** | **20/20** |
| Sync | **512** | 3.364 ms | 0.433 ms | **+2.674 ms** | **20/20** |

這兩個邊界分別對應解碼步數 134 與 390。**每種模式下的 10,000 個測量步數**皆與預期的下一個 Token ID 及記錄的位置推進相符。

序列移除與批次設定在兩種模式的兩個邊界上皆顯示 **0/20 的突刺**。週期性的過高時間（excess）集中在原生解碼區間內。

**觀察結論：** 重現邊界突刺並不需要 Python。在兩種計時模式下，突刺在 `llama_decode()` 呼叫內部依然清晰可見。

> **統計說明：** 局部參考 P50（Local Reference P50）為單次執行中局部中位數的中位數。成對超出量中位數（Median Paired Excess）為單次執行的目標值減去參考值差異的中位數；它不一定等於表中所顯示的兩個 P50 值之間的差額。

### 3.2 明確的同步操作將等待與採樣分開

| 評估前的 Token 數 | 非同步 採樣 P50 | 同步模式 同步 P50 | 同步模式 採樣 P50 |
| :--- | :--- | :--- | :--- |
| 256 | 7.293 ms | 7.119 ms | **0.100 ms** |
| 512 | 7.184 ms | 6.882 ms | **0.099 ms** |

在明確的同步操作之後，採樣大約花費 **0.1 毫秒**，而在同步區間測量到的時間約為 **7 毫秒**。

這支持了一種解釋：非同步採樣區間包含了大量等待未完成 GPU 工作（pending GPU work）的時間。它不應該單純被視為貪婪採樣本身的運算成本。在此計時介入操作後，週期性的解碼突刺依然存在。

### 3.3 首次解碼行為與突刺變異性

首次解碼的 P50 在**非同步模式下為 22.688 毫秒**，在**同步模式下為 22.050 毫秒**。與實驗 6-A 不同，目前的原生實作在預填之後不會立即採樣或明確進行同步。因此，其首次測量到的解碼可能包含未完成的預填工作，無法與 6-A 的第一步直接比較。它被排除在週期性邊界的結論之外。

突刺的幅度（amplitude）也有很大的變化：非同步解碼 P95 在 **256 達到 39.182 毫秒**，在 **512 達到 39.998 毫秒**。可重現的位置並不意味著突刺的成本是固定的，這些測量也無法確立其相較於 Python 路徑具有絕對的效能優勢。

## 4. 結論

週期性的突刺在原生 `llama_decode()` 內部的 Token 位置 256 與 512 處重現，在**兩種模式下皆發生了 20/20 次**。這將該現象定位在受測軟體堆疊（stack）中的原生解碼路徑或更底層，而非肇因於 Python 綁定或高階串流邏輯。

明確的同步操作也顯示，非同步採樣區間大部分的時間代表著在等待 GPU 執行完成。然而，API 的掛鐘時間（wall-clock）測量無法識別出底層的執行階段、CUDA 或驅動程式事件。由於原生預設值與從預填到解碼的過渡階段與實驗 6-A 不同，因此這是一個層級定位（layer-localization）實驗，而非精確的計時等效性測試。

需要進一步的內部儀測（internal instrumentation）來確立其發生機制。
